## Description

`log` forms through `list_records`. `status` keeps its single ledger parse, feeding three consumers
from it.

## Interface contract (produced here)

```rust
RepositoryView::list_of(l: &Ledger, q: &TurnQuery) -> Result<Page<TurnSummary>, CursorError>
```

Mirrors the `health`/`health_of` pair P4 already established for exactly this reason: it takes an
already-parsed `Ledger` so `status` can feed `health_of`, `list_of`, and the eviction set from one
read. Whether `list()` survives as a delegating wrapper or is replaced by `list_of` is this task's
call (open question 2, non-blocking) — `list()`'s existing unit tests exercise it either way.

## `status_report`'s THREE consumers, and which type each needs

Read the **whole** function before wiring — including the over-budget branch. Getting this wrong is
the data-loss path:

| Consumer | Turn set | Fields needed | Source |
|---|---|---|---|
| turn count, rich-rate window | **filtered** (`turns`) | `imported`, `grade`, `tool`, `.len()` | `list_of(&ledger, &TurnQuery{include_all:false})` — all on `TurnSummary`, no widening |
| eviction protect-set (`retention::enforce_budget`) | **UNFILTERED** (`all_turns`) | `prompt_ref` + every `files[]` blob hash | `ledger.records` directly (or `list_records(&TurnQuery{include_all:true})`) — **never** the filtered page |
| health figures | (whole ledger) | — | `health_of(&ledger, budget)` — already wired by P4 |

`enforce_budget` protects `prompt_ref` from **any** turn — its own comment: "protect any blob
referenced as a prompt by ANY turn, not just kept ones" — and derives snapshot hashes via
`turn_snapshot_hashes`. `TurnSummary` carries neither `prompt_ref` nor `files[]`.

## `log`'s two forms

Both go through `list_records` (full `TurnRecord`), because the human line needs `prompt_excerpt`,
`truncated`, and `files_complete` (`fmt::turn_list_line`) and the noise fold needs per-file paths.

**Adapter-transformation rule (design R18) — the only sanctioned reshaping:** the adapter slices
`page.items.iter().rev().take(limit)` **before** calling the renderer (the view returns oldest-first
and limits from the *first* n; `log` renders newest-first with `--limit` default 50, so the limit
cannot be pushed into the query), and applies `fmt::glossary_for` to the renderer's output
**after**. That is why `limit` and `explain` are **not** render opts.

**Sanctioned opts for human `log`, complete:** `now_ms`, `utc`, `color`, `all_files`, and a prebuilt
`NoiseMatcher` (root-derived at *build* time, pure at render time). Nothing else. A closure capturing
a store, ledger, or root counts as a handle and is banned.

## Acceptance criteria

- [ ] **AC16 — the data-loss gate.** `status`'s eviction protect-set is built from the **unfiltered**
      turn set. The fixture **must share hashes** — an earlier version of this AC was theater
      because `enforce_budget` derives `candidates` *only* from the turns passed in, so a blob
      referenced *only* by an excluded turn is invisible to eviction (survives under both
      implementations) rather than deleted. Two loss classes, **both required**:
      - **(a) prompt-protection loss.** One blob that is simultaneously an old, past-boundary
        surviving turn's snapshot hash **and** an excluded **git** turn's `prompt_ref`. Unfiltered:
        `protected_prompts` saves it. Filtered: the git turn is absent, its `prompt_ref` never enters
        `protected_prompts`, and the blob is evicted.
      - **(b) keep-set loss.** One blob shared between an excluded **superseded** turn near the
        ledger tail (inside the keep window when included) and an older surviving candidate turn.
        Unfiltered: `keep` holds it via the tail turn, so the candidate walk skips it. Filtered: it
        is absent from `keep` and is evicted.

      **Backdate blob mtimes past `pass_start`** using the existing `cmds::tests::backdate` helper,
      or `enforce_budget`'s A3(c) same-pass guard rescues the blobs vacuously and the fixture stops
      discriminating. Assert **deletion** under the filtered derivation (RED) and **survival** under
      the unfiltered one.

```
status keeps ONE ledger parse feeding health_of + list_of + the unfiltered

Deriving owned_turns from the filtered page would let eviction delete blobs

referenced only by an excluded turn is invisible to eviction, not deleted, so
a non-sharing fixture would have discriminated nothing.

transformation is .rev().take(limit) before rendering and the glossary after.

```

## Notes

- **Edge cases:** zero-turn repo (`log`, `log --json` → `[]`, `status`); log with only epoch records;
  over-budget store with **no** superseded/git turns (AC16's fixture must not be the only eviction
  test that still passes); a daemon appending concurrently during `status` — all reads are
  ledger-fresh per call, and no read path takes `log.lock`.
- **`--explain`'s glossary** (`fmt::glossary_for`) scans *this invocation's rendered output*, so the
  rewiring must not change what `log` renders or the glossary silently breaks. `log_explain.golden`
  is the instrument.
- `status_json.golden` consumes no turn data, so it is unaffected by the `list_of` rewiring — but
  assert it anyway; it costs nothing and catches an accidental shape change.
