## Description

Move `recall`'s rank-then-verify read into `agentrec-core::view`, leaving `memorycmds::recall_cmd`
as a renderer over typed values. The CLI/future-MCP path only — the hook path stays exactly as it is.

## Location

**Files:** `agentrec-core/src/view.rs` (edit — add types + method), `cli/src/memorycmds.rs`
(edit — `recall_cmd` becomes render-only), `cli/tests/integration.rs` (edit — new assertions).

## Interface contract (produced here; consumed by P4b-5 and, later, MCP 2.2)

```rust
RepositoryView::recall(q: &RecallQuery) -> Result<RecallPage, RecallError>

pub struct RecallQuery { pub query: String, pub k: usize, pub after: Option<Cursor> }

pub struct RecallPage {
    pub page: Page<MemoryHit>,
    pub capped: bool,          // F3 — verify walk stopped at RECALL_VERIFY_CAP
    pub store_corrupt: bool,   // F10 — distinct recall FAILURE, not a healthy empty result
    pub store_empty: bool,     // PD3 — no memory ever recorded, vs no fresh match
}
```

**`MemoryHit` field-level definition (R23 — this task owns it).** It must serialize **byte-identical
to today's `EffectiveJson`**, which is what decision 3 means concretely:

```rust
#[derive(Serialize)]
pub struct MemoryHit {
    pub id: String,
    pub fact: String,
    pub pins: Vec<Pin>,
    pub origin: String,
    pub ts: u64,
    pub retracted: bool,
    pub freshness: &'static str,                              // "fresh" | "stale" | "orphaned"
    #[serde(skip_serializing_if = "Option::is_none")]
    pub reason: Option<String>,                               // omitted entirely when absent
}
```

Field **order** and the `skip_serializing_if` are load-bearing — `serde_json` emits declaration
order, and P4b-1's `recall_json_hits` golden pins the exact bytes.

**`store_empty` is load-bearing, not decoration.** `recall_cmd` today calls `memory::load_effective`
*directly* to split "no memories yet" (stderr, PD3 zero-state) from "no fresh memories match"
(stdout). Without it on `RecallPage` the adapter must reach around the seam to render its own empty
states — a half-bypassed seam, and exactly the defect class this phase exists to close.

**`RECALL_VERIFY_CAP` transport (R23).** `recall_cmd`'s F3 notice embeds the cap number. Pick one and
state which in the commit message: (a) carry the cap on `RecallPage`, or (b) a named `view`
re-export. Either is sanctioned; leaving the adapter reaching into `memory::` is not.

**`RecallError` (R21, open question — non-blocking).** Either `enum RecallError { Io(String) }` or
make `recall` infallible. Today every arm of `memory::recall_impl` and `load_effective_checked`
returns `Ok`, with corruption/deadline/cap surfaced as `RecallOutcome` flags, so no pinned byte
depends on the choice. **Pick one, state it in the commit message.** No downstream task depends on it.

## Renderer contract (design AC17, two streams)

`recall` writes to **both** streams: the F3 capped notice and the "no memories yet" zero-state go to
**stderr**; hits and "no fresh memories match" go to **stdout**. A `-> String` renderer cannot
produce both. Two sanctioned shapes — pick either:

1. `fn render_recall(page: &RecallPage, opts) -> (String, String)` (stdout, stderr); or
2. a `-> String` stdout renderer plus adapter-side `eprintln!` driven **solely** by `RecallPage`'s
   flags (which are view-typed data, so the constraint holds).

**Sanctioned opts for `recall`, complete (design R17):** `now_ms`, `color`, **`query: &str`**.
Nothing else. The query is required because the no-match line is `no fresh memories match "<query>"`
and P4b-1's golden pins it *including the query text* — omitting it was a blocking gate failure in
round 5. A closure or trait object capturing a store, ledger, or root counts as a handle and is
banned; the constraint is on reachability, not type names.

## Acceptance criteria

- [ ] **AC2 (recall half)** All five P4b-1 goldens byte-identical after this task. **RED proof
      required:** a `MemoryHit` omitting any `EffectiveJson` field, or a `RecallPage` without
      `store_empty`, must fail — demonstrate the failure once in-test, then fix.
- [ ] **AC3 (recall half)** `recall --json` stdout ≡ `serde_json::to_string(&view.recall(..).page.items)`
      — the **items**, never the `RecallPage` (serializing the page whole would emit
      `capped`/`store_corrupt`/`store_empty` and break decision 3).
- [ ] **AC4 (recall half)** A field added to `MemoryHit` appears in `recall --json` with no adapter
      edit (prove by adding a temp field in-test).
- [ ] **AC10** `RecallPage::capped` is set when the verify walk stops at `RECALL_VERIFY_CAP`, the
      human adapter still prints the F3 stderr notice, and `--json` still omits it.
- [ ] **AC11** `RecallPage::store_empty` distinguishes an empty store from a no-fresh-match result,
      and both human empty-state outputs are byte-identical to P4b-1's goldens. RED without it.
- [ ] **AC12** `view::recall` performs **zero writes**: `memory.jsonl` length and
      `memory-stats.jsonl` mtime unchanged across a call. (Today all memory-stats writes live in the
      hook path's `inject_memory`; the CLI path writes nothing — preserve that.)
- [ ] **AC15** `rg 'memory::' cli/src/memorycmds.rs` no longer matches **inside `recall_cmd`** —
      including `memory::load_effective`, which a `memory::recall`-only grep would miss. Hook-path
      functions keep their matches. Two stated limits: the `RECALL_VERIFY_CAP` reference needs the
      sanctioned source chosen above, and a module-top `use agentrec_core::memory::…` defeats this
      grep while preserving the coupling — so **AC15 is a tripwire, not a proof**; AC2/AC10/AC11 are
      what actually pin the behavior.
- [ ] **Hook path untouched.** `hook_recall_hard_wall_deadline` passes **unmodified**, and the diff
      shows no change to `recall_for_hook`, `recall_for_hook_with_deadline`, or `cmds::inject_memory`.
      (Review this function-scoped, not with `git diff --stat` — `memorycmds.rs` necessarily changes,
      so a file-granular check can never show this.)

## Notes

- **Edge cases:** empty store vs non-empty store with no fresh match (distinct on the human path
  only — in `--json` both emit `[]`, since the json branch returns before the distinction is drawn);
  corrupt `memory.jsonl` → `store_corrupt`, fail-open posture preserved on the CLI path; a retracted
  memory never reaches `recall` (INV-M2 guarantees every returned entry is `Fresh`), so `reason` is
  always absent on this path — keep the field for the shared `memories` listing.
- `recall` only ever returns `Freshness::Fresh` entries, so the `freshness` field is always `"fresh"`
  here. It stays in the struct because the same shape serves `memories`.
