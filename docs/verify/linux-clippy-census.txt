Linux clippy census — feat/phase-2-tail
=======================================

WHY THIS EXISTS
---------------
clippy.toml's `disallowed-methods` lint (blocking fs reads) cannot see code inside
`#[cfg(target_os = "linux")]` bodies when clippy runs on darwin — those items are
never compiled. The Linux-only paths were swept by hand and
`cli/src/doctorcmd.rs:848` got a `#[allow(clippy::disallowed_methods)]` with a
procfs rationale. This run exercises the lint on a real Linux toolchain.

PASS 2 — THE CONTROL (does the lint actually SEE the Linux-only bodies?)
-----------------------------------------------------------------------
A clean Pass 1 is ambiguous on its own: "zero hits" is equally consistent with
"no violations" and "the lint never compiled those cfg-gated blocks". The
`#[allow]` attributes could not be neutered (read-only on Rust source), so
`--force-warn` was used instead — it overrides `allow` at the source level.

Exact command (CARGO_TARGET_DIR=/tmp/t2):

  cargo clippy --workspace --all-targets --all-features --locked -- \
      --force-warn clippy::disallowed_methods

Result: 276 total suppressed sites re-surfaced workspace-wide, INCLUDING the
Linux-only one:

        2    --> cli/src/doctorcmd.rs:849:28

That is the `std::fs::read_to_string("/proc/sys/fs/inotify/max_user_watches")`
call inside `#[cfg(target_os = "linux")] fn check_inotify`, i.e. exactly the site
carrying the procfs `#[allow]` at doctorcmd.rs:848. Count 2 = the bin target and
its test target, both of which compile the module.

CONCLUSION OF THE CONTROL: the disallowed_methods lint demonstrably compiled and
analysed the `#[cfg(target_os = "linux")]` bodies on this run, and the
doctorcmd procfs `#[allow]` is what suppresses the one known hit. Because cfg
evaluation is uniform per compilation unit, `check_inotify` having been analysed
means every `#[cfg(target_os = "linux")]` item in these crates was analysed too.
Pass 1's clean verdict is therefore meaningful rather than vacuous.

Converse, worth stating: `cli/src/service.rs:695` carries an
`#[allow(clippy::disallowed_methods)]` but appears NOWHERE in the control's
src-path hits — that site is macOS-gated and does not compile on Linux, so this
run says nothing about it. What this run DOES cover is the uncommitted +138 lines
in `cli/src/service.rs`: they were in scope of the clean Pass 1, so the dirty
working tree is measured, not a hole.

Other src-path sites the control surfaced (all pre-existing, all already carrying

CAVEATS
-------
1. Measures the WORKING TREE at HEAD 728b225 plus the uncommitted
   `cli/src/service.rs` change, not the committed tree.
2. aarch64 Linux under a Colima VM, not GitHub's x86_64 ubuntu-24.04 runner.
   Same rustc/clippy version as CI's `stable`, but not the same host triple.
3. `--locked` was added beyond the task's stated command (CI does not pass it);
   it makes a stale lockfile fail loudly on a read-only mount rather than
   obscurely. It cannot mask a clippy hit.
4. On CI: the `lint` job in .github/workflows/ci.yml DOES run this exact command
   on ubuntu-24.04. But `on:` is `push: branches: [main]` + `pull_request` +
   `workflow_dispatch`, and that file's own comment records that
   `workflow_dispatch` is inert until the workflow is on the default branch — so
   pushing `feat/phase-2-tail` alone triggers nothing. It takes a PR (or landing
   on `main`) to exercise the Linux lint leg in CI.
